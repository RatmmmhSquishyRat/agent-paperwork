## Major Issues (SHOULD FIX)

### M1. 读侧(post read / post summary)对 stage-1 命中的非线程文件静默成功, 与写侧行为矛盾
[repos/paperwork-cli/src/cmd/post.rs#L255-L330, L332-L345](c:/Users/15480/Desktop/AIWorkshop/repos/agent-paperwork-wt-v06grammar/repos/paperwork-cli/src/cmd/post.rs)

**Problem**: 三段路径解析的 stage 1 会直接命中任意已存在文件。写侧(send/edit)新增了 `reject_foreign_thread`(post.rs L434-L447)拒绝非线程文件, 但 Read 与 Summary 分支没有对称守卫, 造成新的静默接受面:

```
$ paperwork post read foreign.txt      # 内容为任意非线程文本
ok post.read 0 messages                # exit 0
showing: 0/0

$ paperwork post summary foreign.txt
ok post.summary foreign.txt            # exit 0, title/participants 为空垃圾值
```

而 master 上同样调用会被 `ensure_suffix` 文本规则重路由为 `foreign.txt.post.md` -> not-found exit 1; 且 v0.6 写侧对同一文件报 format 错误 exit 1。读/写对同一文件的判定矛盾, 代理会把"读到 0 条"误判为"线程为空"而非"文件根本不是线程", 属于本轮 diff 新引入的静默错误面(评审焦点 5)。

**Fix**: 在 Read / Summary 分支复用同一守卫(读侧建议提取一个只报告、不落盘的 `check_foreign_thread`, 避免 `thread_read` + `read_to_string` 双读):

```rust
PostCommand::Read { path, .. } => {
    let path = ensure_suffix(path, ".post.md");
    reject_foreign_thread(&path)?;   // 与 send/edit 对称
    ...
}
PostCommand::Summary { path } => {
    let path = ensure_suffix(path, ".post.md");
    reject_foreign_thread(&path)?;   // 置于 !is_file() 检查之前
    ...
}
```

### M2. usage 信封的 --json 探测把 flag 值中的字面 "--json" 误判为 JSON 模式
[repos/paperwork-cli/src/main.rs#L81-L86](c:/Users/15480/Desktop/AIWorkshop/repos/agent-paperwork-wt-v06grammar/repos/paperwork-cli/src/main.rs)

**Problem**: 解析失败后无法取到结构化解析结果, argv 扫描用 `any(|a| a == "--json")` 判断 JSON 模式, 不区分"flag"与"flag 的值"。实测:

```
$ paperwork post send g.md --message "--json"    # --message 值恰为字面量 --json, 缺 --author
{"category":"usage","command":"post.send",...}    # 输出 JSON 信封, 用户从未请求 --json
```

输出协议按 `--json` 与否分流(默认信封 stderr vs JSON stdout), 该误判使默认模式消费方在错误路径上收到 JSON, 与"默认信封"契约不符。方向相反的漏判不存在(真 `--json` 在 `--` 之前必被匹配), 故为单向误报。

**Fix**: argv 扫描需跳过已知会吃值的 flag 的后随 token。最小改法: 维护吃值 flag 集合(`--message`/`-m`/`--author`/`-a`/`--seq`/`--reply-to`/`--mention`/`--title`/`--name`/`--model`/`--description`/`--entry`/`--entry-title`/`--profile`/`--from`/`--to`/`--type`), 扫描时若当前 token 属于该集合(且非 `--flag=value` 自含形式)则同时跳过下一个 token, 再判断剩余 token 是否为 `--json`。

### m1. usage_fix 的 "-开头正文" 教学对不以 '-' 开头的裸 token 也触发
[repos/paperwork-cli/src/main.rs#L225-L229](c:/Users/15480/Desktop/AIWorkshop/repos/agent-paperwork-wt-v06grammar/repos/paperwork-cli/src/main.rs)

**Problem**: 注释与意图是"疑似以 '-' 开头的正文值引导到 --message", 但分支条件只要求 unknown token 不以 `--` 开头且 command 为 post.send/post.edit。实测 `post send tt.md extra-token ...` 的 fix 输出 "if a body value starts with '-', pass it via --message", 而 `extra-token` 并不以 '-' 开头, 指导与错误不匹配(评审焦点 4: 错误指导必须可复制执行/切题)。

**Fix**:

```rust
Some(tok) if !tok.starts_with("--") && tok.starts_with('-')
    && matches!(command, "post.send" | "post.edit") => { /* dash-body 教学 */ }
Some(_) if matches!(command, "post.send" | "post.edit") => { /* 通用 named-flag 教学 */ }
```

### m3. `-m` 与 `--stdin` 相邻时被 allow_hyphen_values 吞并, "--stdin" 成为正文内容
[repos/paperwork-cli/src/cmd/post.rs#L56-L69](c:/Users/15480/Desktop/AIWorkshop/repos/agent-paperwork-wt-v06grammar/repos/paperwork-cli/src/cmd/post.rs)

**Problem**: 实测 `post send f.md -a alice -m --stdin` -> exit 0, 正文被写为字面量 `--stdin`。这是 `allow_hyphen_values` 的固有语义(clap 无法区分"以 - 开头的正文"与"被误放的 flag"), 属文法决策的已知代价; 但 `--stdin` 恰是本命令的兄弟 flag, 是最可能踩中的具体组合, 且无任何提示(静默接受)。建议在 SKILL.md/after_help 显式登记该约定(如 `-m=` 形式), 或在 resolve_body 处对正文恰为 "--stdin" 时附加一条 warning 级提示。属登记/权衡项, 不阻塞。
