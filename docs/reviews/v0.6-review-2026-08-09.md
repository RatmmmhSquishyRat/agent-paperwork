## 6. 并发回归（多进程实测）

方法：`Start-Process` 并发拉起 N 个 `paperwork.exe post send` 独立进程写同一新线程，等待全部退出后正则提取 seq 集合核验间隙/重复。共 7 轮。

| 轮次 | 配置 | 结果 |
|---|---|---|
| 轮 1 | 10 并发 send | 全 exit 0，seq 1–10 无间隙 **PASS** |
| 轮 2 | 10 并发 send | **1 条 exit 1（io, os error 33），seq 缺 1 条 FAIL** |
| r1/r2 | 各 10 并发 | 各 1 条同型失败 **FAIL×2** |
| r3 | 20 并发 | 2 条同型失败（18/20） **FAIL** |
| 混合读写 | 6 写 + 6 读并发 | 全通过（低概率窗口未触发） PASS |
| race 探测 | 15 写 + 15 读 + 15 summary | 1 写者同型失败 **FAIL** |

**结论：并发不变量（seq 无间隙无重复）在「全部成功」前提下成立，但 Windows 下多进程并发 send 以约 10–20% 概率出现 io 失败并丢消息——升级为 BUG-2（Critical）。** 失败消息未写入、文件无损坏、seq 无重复（失败即整体未提交，原子性保持），但调用方收到 io 错误后消息丢失，须重试。既有并发测试（`concurrent_thread_send_safety` 等）为**同进程线程**模型，且 CI 为 Linux——跨进程 + Windows 锁语义的暴露面未被覆盖。

## 7. bug 清单与裁决

### BUG-2 · Critical · Windows 多进程并发 send 间歇失败丢消息（io, os error 33）

> **复核状态（2026-08-09）**：已修复（`a2c8e9c`，锁内预读）· 复测通过——详见 §8。但修复轮新增的回归测试本身 flaky，另立 **BUG-5**（minor，见 §8.3）。

**复现**（zh-CN Windows，worktree release 二进制）：

```
# 并发 10–20 个进程对同一新线程执行：
paperwork post send conc.post.md --author agentN --message msg-N
```

**实际输出**（失败者，两种形态，概率约 10–20%）：

```
error io: 另一个程序正在处理文件的一部分，进程无法访问。 (os error 33)
# 或
error io: IO error at '<path>': <同上中文文案> (os error 33)
fix: check file permissions
```

**期望**：并发 send 全部成功（阻塞等锁），seq 1–N 无间隙。

**根因**（已读码闭环）：`cmd/post.rs` 的 `reject_foreign_thread`（post.rs L434–447，send 前置检查，引入自 v0.5 修复轮 `39156db`，经 `a07ad4c` 合并带入）在**任何锁之外**执行两次全文件读（`thread_read` + 裸 `std::fs::read_to_string`）。另一进程此刻正在 `thread_send` 内持有 fs2（0.4.3，`LockFileEx`）排他字节区间锁——Windows 强制锁语义下，**跨进程对被锁区间的读操作立即失败为 ERROR_LOCK_VIOLATION(33)**（不同于锁获取的阻塞等待）。两种信封形态恰对应两处读：裸 `?` 走 `PaperworkError::Io`（无路径上下文），`thread_read` 走 `IoContext`（fix 文案误导为 "check file permissions"）。Linux flock 不阻断读者，故此缺陷为 Windows 专属潜伏问题，v0.5 起存在、本轮实测首曝。
**影响**：多 agent 并发编排（本工具核心场景）下消息间歇丢失（有错误信号、文件不损坏，但需调用方重试）；fix 文案误导。
**建议修复方向**（供 owner 裁决，QA 不改码）：legacy 检查移入锁内（thread_send 已有 contains_legacy_headers 锁内检测，reject_foreign_thread 可退化为锁内职责），或锁外读对 os error 33 做有界重试；并补**多进程**并发回归（Windows 平台 CI）。
**附带观察**：同一锁外读结构理论上同样暴露 post read/summary 与写者的竞争（本轮 45 个读者进程未触发，概率更低但结构相同）；io 信封消息内嵌 zh-CN OS 文案，附带击穿 ASCII 契约（与 BUG-1 同属 §4 契约面）。

### BUG-1 · Major · `post send --help` 泄漏非 ASCII `§`，违反冻结的纯 ASCII 输出契约

> **复核状态（2026-08-09）**：已修复（`a2c8e9c` ASCII 清除 + `e783957` help ASCII 防线测试）· 复测通过——23 个 help 输出字节级复扫 0 非 ASCII，详见 §8。

**实际输出**：`--reply-to` / `--mention` 两条 help 文本含 `§`（U+00A7，各 2 UTF-8 字节），全 CLI 唯一非 ASCII 输出点（其余 14 个 help 与全部信封抽查均为纯 ASCII）。
