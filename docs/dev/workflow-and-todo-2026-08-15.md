## 一、持续工作流阶段定义（九阶段）

阶段链：调研落盘 → 计划 → 治理文档先行 → 对抗评审闭合 → 实施 → 验证 → 三维评审 → 修复闭环 → 终局门禁。

各阶段允许回退重入（如评审发现缺陷则回到实施/修复），但不允许跳阶段前冲：未落盘的调研不得进入实施，未通过门禁的产物不得推送。

### 1. 调研落盘
- 职责：对任务涉及的全部外部事实（仓库现场 git 取证、上游规格、行业惯例、历史评审结论）做只读核查，并把结论写成仓库内文档。
- 进条件：任务书到达、工作区基线明确（HEAD 哈希 + 测试基线数字）。
- 出条件：调研文档已提交进 docs/researches/ 或 docs/dev/；任何「实施时才知道」的事实空白被登记为台账项。
- 纪律：研究结论必须先落盘再实施；代码变更不得先于其依据的调研文档（owner 明示红线）。

### 2. 计划
- 职责：把调研结论转成可逐条验证的工单序列（编号、依赖序、每项的终态判据）。
- 进条件：调研文档在案、无阻塞级开放项挡路（或阻塞项已有并行承接）。
- 出条件：计划文档落盘（如 v0.5-perfection-plan 形态：债务对照 + 批次清单 + 执行链 + 闭合通则）。
- 纪律：每项工单只有两种合法终态——「修复 + 回归」或「核实无需改 + 实测证据」；不允许第三种「看起来没问题」。

### 3. 治理文档先行
- 职责：行为/协议/文法类变更先改规格（spec/bdd/tdd/README），代码后行；spec 即 SSOT。
- 进条件：计划中标注「涉协议面」的工单立项。
- 出条件：规格集变更已落 docs/ssot/ 并通过 doc-review；实现工单拿到可引用的规格锚点。
- 纪律：实现与规格冲突时以「哪一侧是 SSOT」裁定，不各打五十大板；v0.6 具名文法为例——spec.md §1/§2/§3 为裁决依据。

### 4. 对抗评审闭合
- 职责：对计划与治理文档做多路独立评审（feasibility/agent-ux/ssot/closure 等视角），逐条销账后才放行实施。
- 进条件：被评审文档已落盘且自洽声明完成。
- 出条件：closure 报告给出 findings 销账表（分子/分母吻合）；残留观察项全部登记台账（如 LED-06/07 形态）。
- 纪律：评审报告必带「修复回应销账段」；未销账 finding 不得以「非阻塞」名义失踪。

### 5. 实施
- 职责：按工单序执行代码/文档变更，每工单原子提交（前缀标识类型：feat/fix/refactor/perf/test/docs/style/build）。
- 进条件：上游评审放行；行为锁定测试先行（先冻结既有行为快照，再做迁移/重构）。
- 出条件：全部工单到达终态；工作区无未提交残留（LED-02 形态不允许过夜）。
- 纪律：提交信息携带工单编号与取舍说明（adapt/reject 也要写清）；golden 快照类测试若需重冻，必须单独提交并注明口径变化。

### 6. 验证
- 职责：全量门禁回归 + 现场探针（复现脚本对每个缺陷呈修复后预期形态）。
- 进条件：实施工单全部终态。
- 出条件：`cargo test --workspace --locked` 全绿、`cargo clippy --workspace --all-targets -- -D warnings` 零警告、`cargo fmt --all --check` 通过；复现证据链脚本在案。
- 检查项追加（2026-08-15，任务 #39；触发事件：裁决批 O1 标志撤销漏改 ci.yml 内嵌 smoke，线上两 run smoke×3 失败）：**CI 内嵌脚本面**——凡 CLI 标志增删（尤其裁决类 breaking 变更），验证必查 `.github/workflows/*.yml`（内嵌 smoke）与 `SKILL.md`、`README.md`、`_e2e/*` 的全仓 grep 扫查并逐个命中点处置；内嵌 smoke 非 cargo 测试目标，`cargo test` 拦不住（规则号 FR-1，权威登记点 open-items-ledger 第十五节；事件全记录见 fix-ledger 第九节与 ci-failure-diagnosis-2026-08-15.md）。
- 纪律：测试计数本身是证据（本轮基线 419），门禁报告必须附数字而非「全部通过」字样。

### 7. 三维评审
- 职责：对修复/实施成果做 completeness / correctness / impact 三路独立评审。
- 进条件：验证门禁全绿。
- 出条件：三份评审报告落盘 docs/reviews/，逐条 findings 有明确去向（已闭环/登记/钉住）。
- 纪律：评审发现一律回流修复闭环，不允许「评审完即结束」。

### 8. 修复闭环
- 职责：消化三维评审与深审发现，逐项落 fix-ledger 销账（修复/登记/钉住三分法），并同步刷新台账状态。
- 进条件：评审报告在案。
- 出条件：fix-ledger 销账统计闭合；open-items-ledger 相关 LED 项状态刷新（append-only 新节，不改写历史段）。
- 纪律：台账联动是修复闭环的一部分——LED 状态未刷新视为该 finding 未真正销账（本轮三维评审低-6 即此教训）。

### 9. 终局门禁
- 职责：轮次收尾的最后一道闸——全量测试/clippy/fmt/release 构建 + 版本纪律终检 + 台账终局闭合 + 推送 + 终局报告。
- 进条件：修复闭环出条件满足。
- 出条件：
  1. `cargo test --workspace --locked` 全绿（附计数）；clippy `-D warnings` 零警告；fmt --check 通过；release 构建成功且 `paperwork --version` 与 Cargo.toml 一致（本轮 0.5.0）；
  2. 版本纪律：未发布轮不得 bump 版本、不得打新 tag、CHANGELOG 不得出现新发布段（Unreleased 段允许）；
  3. git 工作区干净；本地领先提交清单盘点；台账追加终局闭合资节；
  4. 推送 origin 并 `git fetch --prune` 核对 origin/master 与本地一致（推送失败如实记录，不阻塞收尾）。
- 纪律：终局报告必须含门禁证据、台账终态统计、遗留 owner 决策项清单、分支/worktree 终态。

## 二、TODO 台账维护规则

1. 唯一台账：docs/dev/open-items-ledger-2026-08-15.md 是本轮唯一未决项台账。fix-ledger、评审报告、执行日志可以各自记细节，但未决项的权威状态只认 open-items-ledger；任何新发现的未决事项第一步动作就是进台账，而非散落在聊天或任务书。
2. LED 编号规则：`LED-xx` 两位十进制递增，只增不复用、不回收；已闭合项保留编号与历史段，状态以 append-only 新节刷新（如第十节对 LED-04/05/13/14 的口径刷新），禁止改写历史节文字。
3. 状态刷新纪律：
   - 状态值：开放 / 进行中 / 已闭合 / 已裁定（登记不改）/ 钉住（已知限制，转 KL-x 备查表）。
   - finding 销账即台账联动：任何修复波/评审轮销账一条 finding，若其对应 LED 项，必须在同一轮追加台账状态刷新节；「台账未刷新 = 未销账」。
   - 追加节必须声明「未改动第 X 至 Y 节」，保证 append-only 可审计。
4. 评审报告销账段惯例：每份 closure/fix 报告必带销账表，字段 = finding 编号 | 终态（修复/登记/钉住）| 证据（提交哈希或实测命令）；计数必须分子/分母吻合（LED-07 即计数笔误被评审抓出的实例）。
5. 登记不改 ≠ 无人跟进：每个开放项必须写明建议负责阶段（修复波/文档轮/合并轮/发布轮/owner 决策），owner 决策项明示等待的裁定问题。
6. 钉住项（KL-x）单独成表，不算开放项；钉住必须附依据（既有判例/spec 段落/测试锁定）。
