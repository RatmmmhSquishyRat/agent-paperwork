## 一、owner 指令原文要点

### ① 每个 tool 的 UX 必须独立完整设计

> 对于每种tool的UX都应该进行独立完整设计, 尤其是post这里参数这么复杂的场景

### ② name 提升为前置必填位置参数

> name是发送消息时候必须要使用的参数, 因此应当作为一个必填参数, 放到靠前位置。也就是类似于: paperwork Post文件路径 使用者的名字 send {有关这个评论的所有参数详情}

### ③ 授权文法自行涌现

> （owner 授权）基于项目设计哲学自行涌现延伸文法。

即：在满足 ①② 两条硬指令的前提下，具体文法形态授权实现方依据项目既有设计哲学（无状态、路径显式、无登录、显式优于隐式、content 参数置末——见 v0_feedbacks.md 与 ADR-011）自行推演确定，无需逐项请示。

## 二、指令解读（落盘时点共识）

1. **目标文件（PATH）与使用者名字（NAME）提升为前置必填位置参数**。PATH 恒为第 1 必填位置参数；NAME 在产生署名的动词（post send / post edit）中为第 2 必填位置参数。
2. **每个 tool（profile / post / brief / contacts / validate）独立完整设计 UX**，不做一刀切式的最小修补；post 因参数最复杂，是设计的重中之重。
3. owner 字面示例 `paperwork <Post文件路径> <使用者的名字> send {...}` 的**意图**（path 与 name 前置必填、细节参数后置）为硬性要求；具体动词位置等文法细节属授权涌现范围（最终文法见 spec.md 总纲）。

**确认途径记录（2026-08-09 rework 轮补记，SSOT 评审 m8）**：本 §二 解读条款由实施方（Lee）基于指令 ③（授权文法自行涌现）推演得出，经编排层（leader/Main）在任务派发与裁定流转中逐轮确认（含 2026-08-09 两轮编排层裁定函）；其中「字面 path-first 文法否决、意图采纳」的关键解读由 design.md §1.1 给出四点论证。截至本文档更新时点，owner 未对上述解读提出异议；若后续 owner 显式追认或翻转，须在本节追加落盘（本文档 §三：翻转须由 owner 显式新指令）。
