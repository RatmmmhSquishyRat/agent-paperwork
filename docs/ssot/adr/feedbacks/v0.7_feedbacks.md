## 二、指令解读（落盘时点共识）

### 2.1 contacts 必须支持完整 CRUD

1. **缺口判定**：contacts 现状仅 create/add/read 三动词（v0.6 spec §2 全表与 `repos/paperwork-core/src/ops/contacts.rs` L1 模块注释「create, add, read」一致）；**update/remove 为真实缺口**，代码、治理文档、`docs/researches/ux-open-items-backlog-2026-08-08.md` 三处均无既有设计（调研核实，见研究文档 §3）。
2. **本轮补齐两动词**（文法增量逐字进 spec §2，详见 spec.md）：
   - `contacts remove <PATH> --profile <P>`：键 = profile 路径（与 add 幂等判据同一口径，`ops/contacts.rs` L74）；未命中 -> not-found exit 1。
   - `contacts update <PATH> --profile <OLD> --new-profile <NEW>`：OLD 未命中 -> not-found exit 1；NEW 已存在 -> already-exists exit 1；label 依 R11 重派生（format-v2 spec §7.3，`docs/dev/format-v2/spec.md` L344）；条目顺序保留；**不支持改 label**（label 是派生数据，不是用户可写键）。
3. **键语义**：条目键恒为 destination（profile 路径字符串），label 是 R11 派生数据（读目标 profile H1，失败回退文件名主干），不可作键、不可手工覆盖。

### 2.2 append-only 论证被否决；锁 + fast fail 为「非并行编辑场景」写路径的基本做法

1. **否决记录**：实施方此前以 append-only 为由不为 contacts 支持 update/remove 的论证路线被 owner 显式否决（§一 (1)「appendonly要干什么?」）。SSOT 中 append-only 条款的适用域本就仅限通信线程：`docs/dev/adr-v1.md` L36-37（DM thread / Post/GDM 为 append-only）、`docs/dev/format-v2/spec.md` L232（§5.8 保留约束，thread 域）、不变量 I1（同文件 L399）；contacts/brief/profile 三格式不在 append-only 条款适用域内（brief 自 v0.3 起即有 remove 动词，`docs/reviews/v0.3-review-2026-08-01.md` L78，本身即反证）。
2. **锁 + fast fail 原则**：凡**非并行编辑场景**的写路径，一律 fs2 `lock_exclusive` 锁内读改写（复刻 `thread_edit` 模式，`ops/thread.rs` L355-521）：冲突时锁定文件阻塞等待；无法持锁的一侧 fast fail（落 io 错误信封 exit 1，fix 提示锁可能被占用、稍后重试），**不允许无锁降级写入**。
3. **适用判定（owner 给出的准则，§一 (3) 第二句）**：「是否使用同样的路径锁，取决于我给出的功能要求是否也适用于同样的机制」。据此判定，本轮适用锁 + fast fail 的写路径为：
   - contacts add（补锁）、contacts remove（新增即带锁）、contacts update（新增即带锁）；
   - brief add、brief remove（补锁）；
   - profile edit（补锁）。
   锁现状缺口核实：全 core 仅 `thread_send`/`thread_edit` 两处 `lock_exclusive`（`ops/thread.rs` L94、L366），上述**六处**写路径（contacts add/remove/update、brief add/remove、profile edit）均为无锁 read-modify-write 或无锁新增路径，一律适用锁 + fast fail（调研文档 §4 缺口表；rework 修订：原「五处」为计数笔误，与本节自列清单及下游 spec §3.9/§6、bdd §12、tdd §8.6(4) 的「六写路径」口径统一为六处）。
4. **Windows 判例承继**：锁内经同一持锁句柄读取文件内容，否则跨句柄读被锁字节区间触发 os error 33（QA BUG-2 教训，worktree 分支 cli-grammar-v0.6 `repos/paperwork-cli/src/cmd/post.rs` L459-469 注释、L485-487）；新写路径复刻该模式。
5. **崩溃窗口判例沿用**：锁内 truncate + rewrite 的崩溃窗口（断电/杀进程丢全文件）沿用 format-v2 spec §5.7 已接受判例（`docs/dev/format-v2/spec.md` L228），本轮不引入 temp+rename 加固。

### 2.3 spec 治理授权：实施方自决，不再逐项请示

1. owner 明示 spec 文档的管理责任在实施方（§一 (3) 第一句）：凡 SSOT 已给出足够设计路线与技术选型依据的细节（profile 动词面维持现状、锁面范围推演、信封字段命名、错误 category 选择等），实施方依既有 SSOT 与既有 spec 体例**自行涌现延伸并落盘**，不得再向 owner 逐项请示。
2. 本条与 v0.5_feedbacks §一.3（授权文法自行涌现）一脉相承：授权范围 = 全部相关设计路线与技术选型；边界 = 不得违背 owner 显式指令（§一 (1)(2)）与 ADR-011 硬约束（stateless / path-explicit / 无登录）。

### 2.4 read 与渐进阅读能力盘点要求

1. owner 要求盘点全部 read 面（§一 (2)）：**profile show（即 read 能力）、profile list、contacts read、brief read、post read/summary** 均须纳入「先看 summary 再选择性或全部查看详情」的渐进阅读审视。
2. 盘点结论（证据链全文见研究文档 §2 与 spec.md 新增「渐进阅读能力登记结案」节）：
   - post：summary -> read 窗口过滤（`--from/--to/--mention/--reply-to/--limit`），U-09 已裁决保留独立动词结案（`docs/researches/ux-open-items-backlog-2026-08-08.md` L22）；
   - brief：read 默认 TOC + `--full` 全量详情（`docs/reviews/v0.3-review-2026-08-01.md` L152「Nice progressive disclosure」）；
   - 真实缺口仅一项：**brief 按条目选择性看详情** -> 本轮以 `brief read <PATH> [--full] [--entry-title <T>]` 补齐（复用 brief remove 的 `--entry-title` 键语义）；
   - profile show / contacts read 为单位置参数 PATH 的直读能力，已满足要求，登记结案。
3. **渐进披露的 SSOT 源头**：pillars session-log 原话「agent读取时候会先读到目录, 然后可以选择直接全量阅读, 或者根据路径自己手动选择性阅读」（`docs/ssot/pillars/paperwork-init-conversation/session-log-2026-07-29-agent-paperwork-user-only.md` L27）；SOTA summary-before-detail 定量证据（`docs/researches/agent-cli-ux-industry-sota-2026-08-08.md` L63、L194 C4）。

### 2.5 SOTA C6 动词白名单扩容裁定（rework 补录，2026-08-09）

1. **如实更正**：SOTA C6 既定动词白名单原文为「create/send/read/list/edit/add/remove/verify/validate/summary」（`docs/researches/agent-cli-ux-industry-sota-2026-08-08.md` L196，共 10 动词）——**不含 `update`**。本文初版 §五 依据表与研究文档 §5.4 曾失实表述为「update 在既定白名单内」，经 SSOT/agent-ux 双评审（Mark M-1、Ryan M-1）指出后于本 rework 轮更正；`remove`/`read` 确在既定白名单内，唯 `update` 不在。
2. **扩容裁定**：`update` 动词经 owner 指令 (1)（contacts 完整 CRUD）天然授权，随本轮 additive 扩展正式纳入命名政策白名单（扩容为 11 动词）；扩容登记同步落 spec.md §2 本轮增量说明与 §7 第 5 条、tdd §8.3（白名单测试以 spec §4 全表与 bdd S-SHORT-02 枚举为准）。
3. **update 与 edit 的语义分工（消费者侧教学，载入 spec §3.6）**：白名单内既有 `edit`（post edit / profile edit 在用），与本轮 `update` 的分工为——`edit` 恒为「对文件自身内容的就地修改」（post 消息正文、profile 字段）；`contacts update` 恒为「条目 destination 路径的换绑」（键控条目的身份替换），contacts 组无 `edit` 动词。两动词作用对象不同，不构成语义重叠；该分工须随 SKILL.md/README 示例向 agent 消费者披露（impl_plan R6）。
